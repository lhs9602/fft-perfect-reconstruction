## 1. 실행한 검사와 결과

### 1.1 숫자 정합 (독립 계산 대조)

- 독립 계산은 `x[n] * cmath.exp(-2j*cmath.pi*k*n/N)` 의 실수부/허수부와 같은 순서의 누적 합이다. 출력 문자열의 가로·세로·누적 실수부·누적 허수부를 `f"{값:.4f}"`(-0.0000 은 0.0000 으로 정규화)와 비교했다.
- 입력 목록: 길이 8 정수 k = 0..7, 길이 8 음수 정수, 길이 4 실수, 길이 1, 길이 2, 길이 16(k = 0..15), 절댓값 1000 초과 8개, 아주 작은 음수 8개. 무작위 60 케이스(N = 1,2,3,4,5,6,7,8,12,16,32, 정수/실수/±2000 범위 값 혼합, 모든 k)도 돌렸다.
- 결과: 무작위 60 케이스에서 **비교한 29528 칸 중 불일치 0**. 길이 8 정수, 음수, 길이 4, 1, 2, 16 은 숫자·머리글 정렬·각도 범위(0..359)·`-0.0000`·X[k] 줄 모두 문제 0.
- 문제가 나온 것은 값이 큰 입력(1000 초과)과 아주 작은 음수 입력뿐이다 (아래 발견 1~3).

### 1.2 머리글 정렬

- 머리글 92행 `"  n      x[n]  angle  horizontal_len  vertical_len    total_re    total_im"` 의 단어 끝 위치 `[3, 13, 20, 36, 50, 62, 74]` 와 행 102행 형식폭(3, 8, 5, 14, 12, 10, 10)의 끝 위치를 비교했다. 정수/보통 크기 입력에서는 7개 열 모두 일치한다 (`[3, 13, 20, 36, 50, 62, 74]`).
- 폭을 넘는 값이 들어오면 어긋난다 (발견 3).

### 1.3 각도 열 (101행, `{degree:5.0f}`)

- 길이 2, 4, 8 은 모든 k, n 에서 정수 도이고 0..359 안이다. 길이 16 은 22.5 의 배수라 소수 도가 나오는데 `:5.0f` 가 반올림한다: `22.5 -> 22`, `67.5 -> 68`, `112.5 -> 112`, `157.5 -> 158`, `202.5 -> 202`, `247.5 -> 248` (짝수 쪽 반올림).

### 1.4 `-0.0000` 검사

- `rounded()` 를 거치는 열(가로, 세로, 누적 둘)에서는 `-0.0000` 이 나오지 않았다. `rounded(-0.0)`, `rounded(-1e-9)` 는 `0.0` 이고 부호 있는 0 은 만들지 않는다.
- **x[n] 열은 `rounded()` 를 거치지 않는다.** `x = [-0.0, 0]`, `[-0.00001, 0]`, `[-0.00004, 0]` 모두 `  0   -0.0000      0          0.0000 ...` 로 찍힌다 (발견 2). WAV 샘플 `-1/32768` 도 `-0.0000` 이다.

### 1.5 "X[k] = (...)" 줄과 "n 을 <step> 칸 간격으로 더한 합" 줄

- 길이 8, k = 1 실제 출력:
  - `X[1] = (-4, 9.6569)`
  - `n 을 4 칸 간격으로 더한 합 = (-4, 0)` (n = 0, 4 항: (1 + -5, 0 + 0))
  - `n 을 2 칸 간격으로 더한 합 = (-4, 4)`
  - `n 을 1 칸 간격으로 더한 합 = (-4, 9.6569)`
- N = 1..20, 모든 k (210 쌍)에서 **마지막 줄(step = 1)의 문자열이 X[k] 줄과 같다**. 같은 순서로 더하므로 부동소수 값도 동일하다. 단 N = 1 은 합 줄이 아예 없다 (발견 7).
- step 열: N=2 → [1], N=3 → [1], N=4 → [2, 1], N=5 → [2, 1], N=6 → [3, 1], N=8 → [4, 2, 1], N=10 → [5, 2, 1], N=12 → [6, 3, 1], N=16 → [8, 4, 2, 1], N=1 → [] (합 줄 없음), N=0 → [].
- `:g` 문제는 발견 1.

### 1.6 dft() 와의 동일성

- dft() 25~29행과 print_dft_steps 94~98행의 코드(주석 제외)를 문자열로 비교: `angle = (2 * math.pi * k * n) / N`, `horizontal_len = x[n] * math.cos(angle)`, `vertical_len = -x[n] * math.sin(angle)`, `total_re += horizontal_len`, `total_im += vertical_len` 5줄이 **완전히 같다** (`same: True`).
- print_dft_steps 안에는 `complex(`, `.real`, `.imag` 가 없다. 복소수 연산에 의존하지 않는다 (실수 `float` 만 쓴다).
- 출력한 X[k] 의 두 값은 `dft(x)[k]` 와 같다 (N = 1..20 모든 k, 차이 없음).

## 2. 발견 (심각도 순)

### 발견 1. `:g` 때문에 X[k] 줄과 부분 합 줄이 표와 다른 숫자를 찍는다 (wrong)

- 파일/함수: dft.py / print_dft_steps, 103행 및 111행
- 코드:
  - `print(f"X[{k}] = ({rounded(total_re):g}, {rounded(total_im):g})")`
  - `print(f"n 을 {step} 칸 간격으로 더한 합 = ({rounded(part_re):g}, {rounded(part_im):g})")`
- 증거 (명령 출력):
  - 입력 `[123456.789, 2345.6789, -3456.7891, 4567.8912]`, k = 0. 표의 마지막 줄 `total_re` 는 `126913.5700` 인데 바로 아래 줄은 `X[0] = (126914, 0)`, 부분 합 줄은 `(120000, 0)` / `(126914, 0)`.
  - 입력 `[100.1234, 0.0]` → 표 `100.1234`, 아래 줄 `X[0] = (100.123, 0)`.
  - 입력 `[1234567.1234, 1.0]` → `X[0] = (1.23457e+06, 0)`, `[12345678.0, 0.0]` → `(1.23457e+07, 0)`.
  - 입력 8개 큰 값(±1234 ~ ±8912), k = 0 → `X[0] = (-4353.54, 0)` 인데 표의 누적은 `-4353.5354`.
- 이유: `:g` 는 유효숫자 6 자리로 줄이고 큰 수에서 지수 표기를 쓴다. `rounded()` 가 이미 소수 넷째 자리로 맞춘 값인데, 절댓값이 100 이상이면 소수 자리가 줄고 1e6 이상이면 `e+06` 이 나온다. 같은 출력 안의 표(`:.4f`)와 숫자가 달라 보인다. 작은 값(|값| < 100)에서만 맞다.
- 제안 교체 (메모리 치환으로 검증, `X[1] = (-4.0000, 9.6569)` 정렬 정상):
  - `print(f"X[{k}] = ({rounded(total_re):.4f}, {rounded(total_im):.4f})")`
  - `print(f"n 이 {step} 씩 커지는 항 (n = 0, {step}, ...) 만 더한 합 = ({rounded(part_re):.4f}, {rounded(part_im):.4f})")`
  - (`:g` 의 "4 가 -4" 같은 군더더기 제거가 목적이면 `{rounded(total_re)}` 도 가능하다. 이 경우 `-4.0` 처럼 찍히고 1e16 미만에서는 지수 표기가 없다.)

### 발견 2. x[n] 열이 `rounded()` 를 거치지 않아 `-0.0000` 이 찍힌다 (misleading)

- 파일/함수: dft.py / print_dft_steps, 102행 `{x[n]:8.4f}`
- 증거: `x = [-0.0, 0]`, `[-0.00001, 0]`, `[-0.00004, 0]`, `[-1/32768, 0.5, 0, 0]`(WAV 샘플 -1) 모두 첫 행이 `  0   -0.0000      0          0.0000        0.0000      0.0000      0.0000`. 같은 행의 다른 열은 `0.0000`.
- 이유: 80행 주석("0.0 을 더해 -0 을 0 으로 만든다")의 목적이 표에서 `-0.0000` 을 없애는 것인데 x[n] 열만 직접 포맷한다. WAV 에서 읽은 `-1/32768 = -0.0000305` 같은 작은 음수 샘플에서 실제로 나타난다.
- 제안 교체: `{x[n]:8.4f}` → `{rounded(x[n]):8.4f}` (메모리 치환 검증: 위 입력 전부 `-0.0000` 0건).

### 발견 3. 열 폭이 고정이라 큰 값에서 머리글과 열이 어긋난다 (misleading)

- 파일/함수: dft.py / print_dft_steps, 92행 머리글과 102행 형식폭
- 증거: `x = [1000.0, 0]`, k = 0 → 첫 행 끝 위치 `[3, 14, 21, 37, 51, 63, 75]`, 머리글 끝 위치 `[3, 13, 20, 36, 50, 62, 74]` (모든 열이 한 칸씩 밀림). 입력 8개 큰 값(±1234 ~ ±8912)은 k = 0..7 의 모든 행(72줄 모두) 어긋남. `-100.0` 도 `-100.0000`(9 자)이라 폭 8 초과.
- 이유: x[n] 열 폭 8 은 -99.9999 ~ 999.9999 만 받는다. `total_re`, `total_im` 폭 10 은 -9999.9999 ~ 99999.9999 만 받는다 (예: 누적이 `-10816.3211` 이면 11 자). n 열 폭 3 은 n ≥ 1000 에서 넘친다. 지침 입력(길이 8, 정수)에서는 문제 없으나, 검토 항목인 "1000 초과 값"에서 깨진다.
- 제안 교체 (메모리 치환 검증: 위 큰 값·작은 음수·길이 16 등 입력에서 어긋남 0건):
  - 92행: `print("  n        x[n]  angle  horizontal_len  vertical_len      total_re      total_im")`
  - 102행: `{x[n]:8.4f}` → `{rounded(x[n]):10.4f}`, `{rounded(total_re):10.4f}  {rounded(total_im):10.4f}` → `{rounded(total_re):12.4f}  {rounded(total_im):12.4f}`

### 발견 4. 표 머리글 `angle` 은 도 단위인데 코드의 `angle` 은 라디안이다 (misleading)

- 파일/함수: dft.py / print_dft_steps, 92행 `angle` 과 94행 `angle = ... # 칸 k, 샘플 n 의 각도 (라디안)`, 101행 `degree = ...`
- 증거: 표의 `angle` 열 값은 `0, 45, 90, ...` (도)인데, 같은 함수의 변수 `angle` 은 `2 * math.pi * k * n / N` 으로 `0, 0.785, 1.571, ...` (라디안). 표에 찍히는 값은 변수 `degree` 다.
- 이유: 머리글이 코드 이름을 그대로 쓰는 표(`horizontal_len`, `vertical_len`, `total_re`, `total_im` 은 변수명과 같다)에서 `angle` 만 변수와 단위가 다르다. 표를 보고 코드를 읽는 학습자가 `angle` = 도로 오해한다.
- 제안 교체: 머리글 `angle` → `degree` 로 하고 폭을 맞춘다 (6 자). 92행 `"  n      x[n]  degree  horizontal_len  vertical_len    total_re    total_im"`, 102행 `{degree:5.0f}` → `{degree:6.0f}` (메모리 치환 검증: 정렬 정상). 발견 3 의 폭 제안과 함께 쓰면 `"  n        x[n]  degree  horizontal_len  vertical_len      total_re      total_im"`.

### 발견 5. 각도 열 `:5.0f` 가 소수 도를 지우고 360 을 찍는다 (misleading)

- 파일/함수: dft.py / print_dft_steps, 101~102행 `{degree:5.0f}`
- 증거: 길이 16, k = 1 → n = 1, 3, 5, 7 의 각도 22.5, 67.5, 112.5, 157.5 가 `22`, `68`, `112`, `158` 로 찍힘 (짝수 쪽 반올림이라 22.5 는 내림, 67.5 는 올림). 같은 행의 `horizontal_len` 은 22.5 도 기준(`1.8478`)이라 표시 각도로 다시 계산하면 안 맞는다. N = 721 의 n = 720, N = 1000 의 n = 999 는 `360`.
- 이유: 검토 기준 "0..359 로 접은 도" 를 N > 720 에서 위반하고, 길이 16 에서 실제 각도를 숨긴다.
- 제안 교체: `{degree:6.0f}` → `{degree:6.1f}` (길이 16 은 `22.5`, 길이 8 은 `45.0`, 범위 359.9 이하는 `.1f` 에서 360.0 이 나오지 않는 N < 7200). 소수 둘째까지 필요하면(N = 32 의 11.25) `{degree:7.2f}` 로 하고 머리글 폭을 맞춘다. (nit 로 취급 가능: 길이 8 이하에서는 영향 없음)

### 발견 6. 라벨 `n 을 {step} 칸 간격으로 더한 합` 이 무엇을 더하는지 말하지 않고 "칸" 의 뜻이 충돌한다 (misleading)

- 파일/함수: dft.py / print_dft_steps, 111행
- 코드: `print(f"n 을 {step} 칸 간격으로 더한 합 = (...)")`
- 증거: 같은 함수 안에서 "칸" 은 주파수 칸 k 를 뜻한다 (85행 "칸 k 하나를 구하는 과정", 89행 "칸 k 의 실수부 합", 94행 "칸 k, 샘플 n 의 각도"). 111행은 같은 낱말을 n 의 간격 단위로 쓰고, 104행 주석은 같은 값을 "n 을 건너뛰는 간격" 이라고 "칸" 없이 쓴다. 더하는 것은 `horizontal[n]`, `vertical[n]`(n = 0, step, 2 * step, ... 번째 항)인데 라벨은 시작이 n = 0 인 것도, 항을 더한다는 것도 말하지 않는다. N = 8, k = 1 의 step = 4 줄은 n = 0, 4 두 항의 합 `(-4, 0)` 이다.
- 이유: 라벨이 코드가 더하는 것(어느 n 의 어느 값)과 정확히 일치하지 않고, "칸" 이 이 파일의 용어(주파수 칸)와 충돌한다. 마지막 줄(step = 1)이 X[k] 와 같다는 것(검증 1.5)도 라벨만으로 알 수 없다.
- 제안 교체: `f"n 이 {step} 씩 커지는 항 (n = 0, {step}, ...) 만 더한 합 = (...)"` (메모리 치환 실행 확인: `n 이 4 씩 커지는 항 (n = 0, 4, ...) 만 더한 합 = (-4.0000, 0.0000)`). 최소 수정은 `칸` 만 빼 `f"n 을 {step} 간격으로 더한 합"`.

### 발견 7. step 주석이 2 의 거듭제곱에서만 맞고 N = 1 은 합 줄이 없다 (nit)

- 파일/함수: dft.py / print_dft_steps, 104~105행, 112행
- 코드: `step = N // 2  # n 을 건너뛰는 간격. N/2 에서 시작해 절반씩 줄인다` / `while step >= 1:  # 간격이 1 이 될 때까지` / `step //= 2`
- 증거: N = 12 → step 6, 3, 1 (3 의 절반은 1.5 인데 1), N = 10 → 5, 2, 1, N = 6 → 3, 1, N = 3 → 1 만. N = 1 은 `1 // 2 = 0` 이라 `while step >= 1` 이 한 번도 안 돌아 합 줄이 0개다 (X[k] 줄만 나옴). 반면 N = 2 는 `1` 한 줄이고 X[k] 와 같다.
- 이유: "절반씩", "1 이 될 때까지" 가 N = 2^m (m ≥ 1) 에서만 정확하다.
- 제안 교체: 104행 `# n 을 건너뛰는 간격. N // 2 에서 시작해 2 로 나눈 몫으로 줄인다 (N 이 1 이면 0)`, 105행 `# 간격이 1 이상인 동안`, 112행 `# 간격을 2 로 나눈 몫으로 줄인다`.

### 발견 8. 101행 주석이 "각도를 도 단위로 바꾼다" 고 하지만 `angle` 을 바꾸지 않는다 (nit)
