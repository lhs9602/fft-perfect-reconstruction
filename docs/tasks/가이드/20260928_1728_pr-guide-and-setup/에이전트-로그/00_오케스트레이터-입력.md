# 오케스트레이터 입력

**TL;DR**: 검토 노드 3개를 병렬로 돌려, 사본에 써 둔 함수 위 공식 주석 6개와 DFT 출력 함수가 코드와 맞는지 서로 다른 관점으로 반박하게 했다. 노드는 파일을 고치지 않고 지적만 돌려준다. 고치는 일과 사용자 승인은 오케스트레이터가 한다.

## 원본 입력

> 공식: X[k] = Σ x[n] * (cos(θ) - j*sin(θ)) / θ = 2πkn / N / 합산 범위: n = 0 ~ N-1
> 기호: N, n, k, x[n], X[k], j (설명 여섯 줄)
> 이런식으로 함수들 위에 주석을 넣어줘.
> 그리고 DFT쪽들 코드를 수정해서 니가 출력한 내용을 한눈에 볼수 있게 해줄 수 있어?

## 요구 해석

- 함수 위 주석: 변환 함수 6개(`dft`, `idft`, `bit_reverse_order`, `twiddle_table`, `fft`, `ifft`) 위에 사용자가 보낸 형식(공식, 기호)의 `#` 주석 블록을 둔다. 공식이 없는 함수(`read_wav`, `write_wav`, `restore_no_overlap`, `main`)는 그대로 둔다.
- DFT 출력: 선택지 질문은 사용자가 닫았다. 직전 설명에서 보여 준 두 가지(칸 하나의 n별 표, n을 건너뛰며 더한 합)를 모두 출력하는 `print_dft_steps(x, k)`를 `dft.py`에 두는 것으로 정했다. 적용 전 전후 제시와 승인에서 사용자가 바꿀 수 있다.
- 사용자는 앞서 "주석이 코드와 안 맞는다, 재검토하라"고 지적했다. 그래서 주석과 코드의 일치를 독립적으로 확인한다.

## 위임 설계 근거

- [x] 왜 이 분해(노드 3개)인가 — 검토 대상이 성격이 다른 세 덩어리다: `dft.py`의 공식 주석 2개, `main.py`의 공식 주석 4개와 고친 줄 주석 3개, 새 출력 함수. 덩어리마다 확인 방법이 달라(식 대조, 식 대조와 기호 충돌, 실행 대조) 관점을 나눴다.
- [x] 어떤 패턴·왜 — adversarial-verify(병렬). 노드끼리 결과를 주고받을 필요가 없고, 저술(오케스트레이터)과 검증(노드)을 나눈다.
- [x] 모델·effort 배분·왜 — Sonnet, effort 는 세션 상속. 식 대조와 실행 확인이라 상위 모델이 필요 없다.
- [x] 폭주 방지 — 노드는 사본 폴더만 읽고, 쓰는 파일은 자기 로그 하나뿐이다. 반환은 지적 목록(구조화)으로 제한한다.
