# 오케스트레이터 입력

**TL;DR**: 검토 노드 3개를 병렬로 돌려, 오케스트레이터가 쓴 `docs/가이드/11_개념 흐름 설명.md`를 사실 검증, 처음 읽는 사람의 이해, 문서 규칙 세 관점에서 반박하게 했다. 노드는 문서를 고치지 않고 지적만 돌려준다.

## 원본 입력

> 내가 아직 개념이 헷갈려 dft 단계부터. 차근 차근 설명하는 문서를 만들어줘. 특히 (09 §1.3 "cos와 sin — 화살표 끝의 가로 거리와 세로 거리"의 앞부분 인용) 이러거 보면 이걸 왜 구하는지 뭘 의미하는지, 공식 결과가 뭘 의미하는지 이런 개념이 안잡혔어. 내가 이거보고 설명이 가능할 정보로 자세히 적어줘.

## 요구 해석

- 09와 10은 식을 세우는 걸음(어떻게)을 적었다. 사용자가 빠졌다고 한 것은 **왜 구하는가, 무엇을 뜻하는가, 결과가 무엇을 뜻하는가**다. 그래서 새 문서는 절마다 "왜 필요한가, 무엇을 하는가, 결과가 뜻하는 것, 숫자로 확인, 한 문장으로 말하면"의 같은 순서로 쓴다.
- "dft 단계부터"는 DFT에서 시작해 그 뒤 단계(역 DFT, FFT, 윈도우, 겹침)까지로 읽었다. 무게는 DFT와 역 DFT에 둔다.
- "설명이 가능할 정도"를 위해 통째로 말하기(§12), 자주 받는 질문(§13), 스스로 확인하기(§14)를 넣었다.
- 예는 샘플 8개짜리 하나(1번 출렁 세기 3 코사인 + 2번 출렁 세기 2 사인)로 끝까지 잇고, 윈도우와 겹침만 실제 값(512, 16, 16 kHz)으로 보였다.
- 숫자와 그림 8장은 `src/dft.py`, `src/main.py`의 함수로 계산했다. 출력은 `첨부_이력_개념 흐름 검산 출력.txt`다.

## 위임 설계 근거

- [x] 왜 이 분해(노드 3개)인가 — 확인할 것이 세 갈래이고 방법이 다르다: 숫자와 주장의 사실 여부(다시 계산, 근거 문서 대조), 읽는 사람이 실제로 이해하는가(독자 시점으로 읽고 답해 보기), 문서 규칙(머리말, 근거 표기, 링크, 다이어그램, 그림과 글의 일치).
- [x] 어떤 패턴·왜 — adversarial-verify(병렬). 저술은 오케스트레이터가 했고(확정된 범위의 긴 글), 검증만 나눈다.
- [x] 모델·effort 배분·왜 — Sonnet, effort 는 세션 상속.
- [x] 폭주 방지 — 노드는 문서와 코드를 읽기만 하고, 쓰는 파일은 자기 로그 하나다. 반환은 지적 목록(구조화)으로 제한한다.
