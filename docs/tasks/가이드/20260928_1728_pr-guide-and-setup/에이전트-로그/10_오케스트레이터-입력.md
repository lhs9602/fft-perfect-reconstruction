# 오케스트레이터 입력

**TL;DR**: 검토 노드 3개를 병렬로 돌려, 사본에 써 둔 겹침 있는 복원(함수 5개, `main`의 실행 줄, 시험 6개)을 사양 일치, 주석과 코드의 일치, 시험의 검출력 세 관점에서 반박하게 했다. 노드는 검토 대상을 고치지 않는다. 고치는 일과 사용자 승인은 오케스트레이터가 한다.

## 원본 입력

> 주석 처리하고 overlap과 윈도우 쪽도 구현하자. FFT 쪽도 변경사항이 있나?

## 요구 해석

- "주석 처리하고": `main`의 겹침 없는 FFT 복원 세 줄을 주석으로 돌린다(DFT 복원 때와 같은 방식).
- "overlap과 윈도우 쪽도 구현하자": 가이드 04의 단계_5(Hanning 윈도우), 단계_6(프레임 공급), 단계_7(분석), 단계_8(합성)을 `main.py`에 구현한다. 사양은 03의 공식_9 ~ 공식_16과 04의 "할 일", "확인" 표에 이미 정해져 있다.
- "FFT 쪽도 변경사항이 있나": `fft`, `ifft` 자체는 바꾸지 않는다. 답으로 전한다.
- 직전까지 사용자는 코드 작성을 Claude에게 직접 맡겨 왔다. 이번에도 구현을 맡긴 것으로 읽고, 적용 전 전후 제시와 승인에서 확인받는다.

## 위임 설계 근거

- [x] 왜 이 분해(노드 3개)인가 — 확인할 것이 세 갈래다: 사양(공식, 자리 계산, 프레임 수)과의 일치, 새 공식 주석과 줄 주석이 코드와 맞는지, 새 시험이 흔한 실수를 잡아내는지. 서로 확인 방법이 다르다(독립 재구현 대조, 글자 대조, 일부러 틀리게 해 보기).
- [x] 어떤 패턴·왜 — adversarial-verify(병렬). 저술(오케스트레이터)과 검증(노드)을 나누고, 노드끼리는 결과를 주고받지 않는다.
- [x] 모델·effort 배분·왜 — Sonnet, effort 는 세션 상속. 수치 대조와 글자 대조라 상위 모델이 필요 없다.
- [x] 폭주 방지 — 노드는 검토 대상 사본을 읽기만 한다. 일부러 틀리게 해 보는 노드만 자기 전용 복사본을 따로 만들어 고친다. 쓰는 파일은 자기 로그 하나다. 반환은 지적 목록(구조화)으로 제한한다.
